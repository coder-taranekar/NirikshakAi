## Architecture Pattern

The backend follows a layered separation of concerns:

```
Router (thin controller) → Service (business logic) → Model/Database
```

- **Routers** handle HTTP, validate request schemas, call services, return response schemas
- **Services** contain all business logic (OCR, compliance engine, report generation, etc.)
- **Models** are pure ORM definitions — no business logic
- **Schemas** (Pydantic) are separate from models — never return ORM objects directly from routes
- **Rules** (`rules/`) will hold YAML-driven compliance rule configs consumed by the compliance engine service

## Models — Conventions

All models follow these conventions:

1. **Two shared mixins** (always applied via multiple inheritance):
   - `UUIDPrimaryKeyMixin` — UUID PK, server-generated by PostgreSQL `gen_random_uuid()`
   - `TimestampMixin` — `created_at` + `updated_at` (timezone-aware, server-set)

2. **SQLAlchemy 2.0 style** — use `Mapped[type]` + `mapped_column()`, never the legacy `Column()`

3. **Python enums for status fields** — all enums extend `str, enum.Enum` so values serialize as plain strings; enums are stored as PostgreSQL native ENUMs

4. **JSONB for structured data** — `ocr_result` and `compliance_result` on `Inspection` are JSONB columns; their schemas are documented in docstrings and README

5. **`lazy="dynamic"` on collection relationships** — allows query chaining (`.filter()`, `.count()`) without loading all records

6. **`__repr__` on every model** — include `id` and the most meaningful identifying fields

7. **Module-level docstring on every file** — explain purpose and any non-obvious design decisions

## Naming Conventions

- **Migration files**: `YYYYMMDD_HHMM_description.py` (date-prefixed)
- **Router files**: named after the domain they serve (`auth.py`, `manufacturers.py`, etc.)
- **Service files**: named after the service (`ocr_service.py`, `compliance_engine.py`, etc.)
- **Inline section comments**: `# ── Section Name ──────────────` style used throughout
- **Environment**: snake_case for all env var names; settings attributes mirror them

## Key Entities & Relationships

```
User ──────────────────────────── registers ──► Product
  │                                                │
  │ inspects                                       │ belongs to
  ▼                                                ▼
Inspection ◄───── product_id ───────────── Product ◄─── Manufacturer
  │                                                         │
  └── violation_records ──► ViolationRecord ◄── manufacturer_id ──► Manufacturer
```

- `User` roles: `inspector` or `admin`
- `Product` optionally links to a `Manufacturer`; `is_schedule_ii_commodity=True` marks products used for pack-size lookup
- `Inspection` is the core pipeline result; links to a `Product` and the `User` (inspector)
- `ViolationRecord` is the cross-state registry entry; links to both `Manufacturer` and `Inspection`
